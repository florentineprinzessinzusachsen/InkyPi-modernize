# CLAUDE.md

Guidance for Claude Code when working in this repository. This file is a reference for conventions, architecture, and APIs — not a changelog. Keep entries here durable and forward-looking; don't record dates, "fixed on X", or debugging narratives.

## Repo context

- This is a **private fork of `jtn0123/InkyPi`** (itself a heavily-diverged fork of the original `fatihak/InkyPi`). `origin` is the private repo (`florentineprinzessinzusachsen/InkyPi-jtn0123`) — real commits and pushes happen here. `upstream` (jtn0123, push-disabled) is kept for pulling future updates — check `git log main..upstream/main` occasionally; when something there looks relevant, `git cherry-pick` it directly (test with `--no-commit -n` first, then reset, if you want to preview before committing). `fatihak-fork-origin` remote / `fatihak-main` local branch is an older private fork, kept only as reference — not the active line of work.
- **`gh` has no default repo configured**, and with four remotes present, a bare `gh pr view <N>` / `gh pr list` silently resolves against whichever repo `gh` picks — not necessarily `origin` — with no error to signal the mismatch. This produced real, confusing wrong-repo results (PR numbers that "exist" but are entirely unrelated PRs from `upstream` or a `fatihak-*` fork). Run `gh repo set-default florentineprinzessinzusachsen/InkyPi-jtn0123` once per environment, or pass `--repo florentineprinzessinzusachsen/InkyPi-jtn0123` explicitly, before trusting any `gh pr`/`gh issue` output.
- **Avoid modifying core InkyPi application code where a plugin-local alternative exists.** Most plugin logic (`src/plugins/<plugin_id>/<plugin_id>.py`, its `render/`, its Python) stays self-contained. **Exception, specific to this fork:** the settings-page system is schema-driven, and a settings-page widget needing genuinely new interactivity (not just a new field type) has no plugin-local mechanism — it requires additions to the shared `src/static/scripts/plugin_schema.js` and a new file in `src/templates/widgets/`. That's an accepted, narrow exception; it does not extend to other core files (`src/inkypi.py`, `src/blueprints/*.py` route logic, `src/refresh_task/`, etc.) without flagging it first.

## Dependabot / branch maintenance

- **A merged/closed dependabot PR's remote branch can look alive when it's not, or vice versa.** GitHub's own `--delete-branch` cleanup doesn't update your local `git branch -r` view — run `git remote prune origin` (or `git fetch --prune`) before trusting that listing. Conversely, a branch with zero associated PR in `gh pr list --search` may still have one — that search endpoint can miss matches; confirm via the REST API (`gh api repos/<owner>/<repo>/pulls?state=all&head=<owner>:<branch>`) before deleting anything, since a truly PR-less branch (superseded before a PR was ever opened) is safe to delete but one the search just missed is not.
- **When a dependabot PR won't auto-rebase** after `@dependabot rebase` (conflicts with other since-merged dependency bumps in the same lockfile), resolve it yourself rather than waiting indefinitely: fetch it (`git fetch origin pull/<N>/head:<branch>`), merge current `main` into it inside an **isolated `git worktree`** (never the main checkout if it has uncommitted work), resolve conflicts, fast-forward local `main` to the resulting merge commit, push, then close the PR referencing the commit.
- **Check a tool's *actually-installed* version before changing its config schema** — don't trust conversation history or an in-flight PR's existence as proof a bump landed. `pyproject.toml`'s `[tool.mutmut]` was nearly rewritten for mutmut 3.x's key names (`source_paths`/`pytest_add_cli_args*`) while the pinned version was still 2.5.1 (`grep '^mutmut==' install/requirements-dev.txt` would have shown this immediately) — 2.5.1 silently ignores unknown keys rather than erroring, so the old, correct keys (`paths_to_mutate`/`tests_dir`/`runner`/`dict_synonyms`) would have quietly stopped working instead of loudly failing.
- **`uv lock` does not float an already-satisfied version range to latest on its own** — it keeps prior resolutions stable across runs. A dependabot PR bumping a production package that already had a loose `pyproject.toml` range (e.g. `numpy>=2.0,<3`) needs `uv lock --upgrade-package <name>` (repeatable per package) to actually pick up the newer version; a bare `uv lock` only reacts to a *changed* constraint (e.g. a bumped exact pin).

## Working conventions

- Only run the test suite (full or scoped) when explicitly asked — it's ~5000 tests, ~3 minutes. For verifying a change, prefer something narrow: a single test file, a targeted manual check via the dev server, or a compile/syntax check.
- `src/config/device_dev.json` is now gitignored (like the old fatihak-based fork's equivalent live-state file) — it kept getting dirtied with real playlist/instance/timestamp data from routine dev-server use, and staying tracked meant that noise repeatedly needed diffing-and-reverting before any real commit. It still exists on disk as a working dev fixture; git just no longer tracks its churn.
- Always `lsof -i :<port>` before killing a bound process — don't assume. Once confirmed as this project's own dev server, it's fine to restart it yourself when needed (e.g. after a code change, since it doesn't hot-reload) without asking each time.
- Don't add a backend Flask blueprint for a plugin's settings-page data needs. If a settings-page widget needs live external data (autocomplete, lookups), check whether the external API sends `Access-Control-Allow-Origin: *` first (`curl -i <url> -H "Origin: http://localhost:8080"`) — public read-only APIs very often do, and calling them directly from client-side JS avoids a backend route entirely.
- Manual verification (forcing plugin refreshes, running the dev server) writes to `src/static/images/current_image.png` — already gitignored, same as `device_dev.json` (see above), so neither needs diffing-before-cleanup anymore.
- Don't over-test every edge case with screenshots. The user tests visually themselves, faster than a screenshot-render-read loop. Do a quick sanity check (runs without error, core case looks right) and stop; reserve a closer look for genuinely new logic, and even then prefer a targeted check (print computed values) over a screenshot sweep.

## macOS dev-environment gotchas (found in jtn0123's own code, not this fork's bugs)

- **Plugin subprocess execution can SIGSEGV on macOS** if forked from this app's always-multi-threaded parent (waitress threads + refresh_task thread) — a plugin's first post-fork `requests`/`urllib` call triggers macOS proxy autodetection (`_scproxy` → CoreFoundation), which is not fork-safe. `worker.py::_get_mp_context()` prefers `spawn` over `fork` on non-Linux for this reason. Linux (the real Pi target) still uses `forkserver`/`fork` — this crash class doesn't exist there.
- The app sets `Referrer-Policy: no-referrer` on every response (`security_middleware.py`), which breaks the Leaflet map in the `weather-map` widget (OSM rejects tile requests with no Referer). `/plugin/<plugin_id>` overrides to `Referrer-Policy: strict-origin-when-cross-origin` on its own response only.
- `install/requirements-dev.txt` is pip-compiled from a *manually maintained* duplicate list (`requirements-dev.in`) — nothing currently checks it automatically stays in sync. Regenerating it wholesale via `pip-compile` on macOS **reliably drops every `sys_platform == "linux"`-gated entry** (e.g. `memray`) instead of preserving it with the marker. Verify by grepping the regenerated output for `sys_platform` and diffing the count against `requirements-dev.in`'s own gated entries before trusting the result; restore any dropped entry's exact hash block from git history rather than re-deriving it.

## InkyPi plugin architecture

- **Contract:** `src/plugins/<id>/<id>.py` defines a class extending `BasePlugin` (`src/plugins/base_plugin/base_plugin.py`), implementing `generate_image(self, settings, device_config) -> PIL.Image`. Raise `RuntimeError` with a clear message on unrecoverable failure — surfaced to the user.
- **`plugin-info.json`** wants `{display_name, id, class, api_version, version}` — `api_version`/`version` are optional (missing just logs a notice), but add them for parity with built-in plugins.
- **Settings pages are schema-driven — enforced, not optional.** `tests/unit/test_legacy_settings_cleanup.py` fails the build if any plugin (other than `base_plugin`/`year_progress`) lacks a `build_settings_schema()` override, or has a `settings.html`. The old "custom `settings.html` + inline JS" pattern is dead here.
  - DSL lives in `plugins.base_plugin.settings_schema`: `schema(*sections)`, `section(title, *items)`, `row(*fields)`, `field(name, type, label=..., options=..., visible_if={...}, ...)`, `option(value, label)`, `option_group(label, *options)`, `callout(text, tone=...)`, `widget(widget_type, template=..., config={...})`.
  - Field types: `text`/`url`/`number`/etc, `checkbox` (needs `submit_unchecked`/`checked_value`/`unchecked_value` to submit a value when unchecked), `radio_segment`, `select` (supports `options_by_value`), `color`, `textarea`, `hidden`.
  - `visible_if={"field": name, "equals"|"operator": ...}` is single-field only — no compound AND/OR. Design around that (a field needing multiple conditions may just need to always show).
  - **Widgets** are for anything a field type can't express (maps, repeaters, live external lookups). A widget = a template in `src/templates/widgets/<name>.html` (rendered via `{% include item.template %}`, gets `plugin_settings` in scope) + a JS init function registered in `plugin_schema.js`'s `widgetInitializers` map, called as `init(widgetElement, config)`. Reusable ones: `weather-map` (single lat/long picker), `calendar-repeater` (multi-entry list with parallel bracket-arrays, e.g. `calendarURLs[]`/`calendarColors[]` — the convention for new multi-entry lists when fields parallelize cleanly; use one-JSON-blob-per-row instead when they don't, e.g. `abfahrtzeiten`'s 5-field stop entries). Modals inside a widget manage their own show/hide directly (`hidden` attribute + `style.display` + a class) — no global `openModal()`/`closeModal()`.
  - `foo[]` fields auto-collect into a Python list via `parse_form()`'s `request_form.getlist`.
  - A plugin needing its declared `api_key` to be conditional on another setting (e.g. only one of several providers actually needs a key) can implement an optional `api_key_required_for_settings(self, settings) -> bool` hook — `blueprints/plugin.py::plugin_page()` calls it once the instance's real settings are known and uses the result to override `required`. This only affects page-load evaluation (correct after save+reload); it doesn't make a disabled Save/Preview button reactively re-enable on an unsaved dropdown change, since no generic frontend wiring for that exists yet.
- **Timezones: `zoneinfo`, not `pytz`** (`pytz` isn't a dependency here). Use `utils.time_utils.get_timezone(tz_name) -> tzinfo` (falls back to UTC on invalid input).
- **`device_config`**: `.get_resolution()`, `.get_config(key, default)`, `.load_env_key(name)`. Declare a required API key via `template_params['api_key'] = {"required": True, "service": ..., "expected_key": "ENV_VAR_NAME"}` in `generate_settings_template()` — entered through `/settings/api-keys`, never a custom form (see API keys section below).
- **No plugin-level backend routes.** Workaround: direct client-side `fetch()` against CORS-permissive external APIs.
- **Plugins render in an isolated subprocess** (`refresh_task/executor.py`/`worker.py`), not in-process, for crash isolation (see the macOS fork/spawn gotcha above). Only the rendered image crosses back over the process boundary (via a tempfile path in the result queue) — any other mutation an `execute()` makes on a passed-in object (e.g. `PlaylistRefresh` setting `plugin_instance.latest_refresh_time`) happens on that process's own copy and is silently lost. If something needs per-instance state to survive a refresh cycle, don't mutate it inside `execute()` — replicate the decision in the parent process (`task.py::_perform_refresh()`, after a successful `_execute_with_policy()` call) using data it already has.
- **CSRF**: session-cookie-based token, required on all non-safe-method requests except a short exempt list. Token via the `csrf-token` meta tag in `base.html`, or `{{ csrf_token() }}` in a form. When scripting requests (curl) against `/preview_now`, `/update_now`, or other POST routes, GET a page first to establish the session + grab the token.
- **`/preview_now` (POST) + `/preview_now_image/<plugin_id>` (GET)**: renders from submitted form settings via `plugin.generate_image()` directly and writes a per-plugin-id scratch PNG (`plugin_image_dir/_preview_scratch_<plugin_id>.png`) — no display push, no history, no persisted settings. This is what the settings page's Preview button uses. **`/update_now`** is the older, different route: it also pushes the render to the real/mock display, records history, and updates `device_config.refresh_info` — a real refresh in every sense except `refresh_type`. Don't conflate the two; use `/preview_now` for anything that should be a look-but-don't-touch preview.
- **`/__smoke/render`**: opt-in (only registered when `INKYPI_SMOKE_FORCE_RENDER=1`), CSRF-exempt, calls `plugin.generate_image({}, device_config)` in-process — no subprocess, doesn't push to display. Good for "does this plugin's render logic run at all" but the empty `{}` settings means it can't exercise a specific instance's real config, and it doesn't exercise the subprocess path.
- **Faster technique for "does this instance actually render correctly":** in a one-off script, `INKYPI_ENV=dev` + `config.Config()` + `plugins.plugin_registry.get_plugin_instance(device_config.get_plugin(plugin_id))`, pull real settings from `device_config.get_config('playlist_config')['playlists'][...]['plugins'][...]['plugin_settings']`, call `plugin.generate_image(settings, device_config)` directly. Skips browser/refresh_task/subprocess. For a blank-render check: `np.array(image.convert('RGB')).mean()` — 255 means solid white.
- **HTML-render plugins referencing `{{static_dir}}` must set it themselves.** `render_image()`'s Jinja environment (`self.env` in `base_plugin.py`) is a bare `jinja2.Environment`, not Flask's — no `static_dir`/`url_for` global. Any plugin template doing `<script src="{{static_dir}}/scripts/foo.js">` needs `generate_image()` to set `template_params["static_dir"] = self.to_file_url(resolve_path("static"))` before `self.render_image(...)` (pattern: `weather_de.py`). Without it the tag resolves to a dead relative path, the JS library never loads, and the plugin silently produces a **100% blank image with no Python-side error** — the failure is a browser-side `ReferenceError` inside headless Chromium, invisible to backend logs. `calendar.py`/`calendar_auth.py` have this fixed; **`weather.py`'s `chart.js` reference does not.**
- **Multi-URL/multi-provider plugin fetches should be concurrent**, via `concurrent.futures.ThreadPoolExecutor`, not a sequential for-loop — `calendar.py`/`calendar_auth.py` (multiple calendar URLs), `abfahrtzeiten.py` (multiple stops), and `weather_de.py` (2-3 calls per provider) all do this now. Use `.map()` when every item is fetched the same way and any failure should abort the batch (calendar's case — matches `executor.map()`'s "re-raise first exception on iteration" behavior); use `.submit()`/`.result()` per named call for a small fixed set of different calls (weather_de's per-provider branches); wrap the fetch in its own try/except *inside* the worker function when per-item failure isolation matters (abfahrtzeiten's per-stop case — a bad stop must not cancel the others). Cap `max_workers` sanely (e.g. `min(len(items), 8)`). Use the shared `utils.http_client.get_http_session()` (connection-pooled, built-in retry policy) instead of bare `requests.get()`/`requests.Session()` for any new fetch code. `regenalarm` is single-location (one fetch) — no concurrency opportunity there.

## Frontend / dark-mode design-system conventions

- Dark-mode UI borders (`--surface-border`/`--panel-border`/`--border-strong` in `_tokens.css`) should read at roughly **3:1 contrast** against that aesthetic's `--surface` (WCAG's non-text-contrast minimum) — anything much lower is effectively invisible. `panel-border` should equal `surface-border` unless there's a specific reason to differ; keep both in sync across all three aesthetics (console/paper/minimal) when tuning.
- Custom (non-built-in) plugin icons ship as flat black-line PNGs with no `PLUGIN_ICON_MAP` entry (`templates/macros/icons.html`), so they render as raster `<img>` instead of the built-in plugins' `currentColor` inline `<svg>` — black-on-transparent art has nothing to adapt with in dark mode. `_plugins.css` gives `img.icon-image`/`img.app-icon`/`img.plugin-icon` (the `img`-element selector deliberately excludes the built-ins' `svg.*` variants) a light, theme-independent backing plate (`var(--eink-paper-bg)`) across all three render contexts (settings-page header, dashboard catalog, playlist row). Any new custom plugin's icon needs this same treatment — either rely on the existing CSS or add a `PLUGIN_ICON_MAP` entry with an equivalent Phosphor icon.
- `.icon-button` is a large-square-tile primitive (`height: 90px`, `aspect-ratio: 1` — for grid icon-picker tiles). Reusing it for anything else (e.g. an inline repeater row's remove button) inherits that sizing unless explicitly overridden, and combined with a flex row's `align-items: stretch` can silently stretch a sibling input to match. `.compact-repeater-toolbar .remove-btn` overrides this back to 44px for the calendar/calendar_auth/todo_list repeater widgets — check for the same trap if a new widget reuses `.icon-button` in a row.
- The plugin settings page's Preview card is a single full-width "this plugin instance" image (`.status-bar` in `_preview.css` is one column) — there is no side-by-side "current display" comparison card anymore.

## API keys / custom secrets

- `/settings/api-keys` (GET, `settings.api_keys_page` in `blueprints/settings/_config.py`) is the only API-keys page — renders the 6 fixed provider cards (`_FIXED_PROVIDER_KEYS`) and a "Custom secrets" section for everything else in `.env`, via the same `api_key_card` macro for both.
- Saving: `POST /settings/save_api_keys` handles both fixed and custom keys in one request — any submitted field matching `_CUSTOM_KEY_NAME_RE` (`^[A-Za-z_][A-Za-z0-9_]*$`) that isn't a fixed key or an internal key gets written via `device_config.set_env_key()`. Deleting: `POST /settings/delete_api_key`, same name-validation.
- This is the mechanism any plugin needing a per-instance or arbitrary secret should use (ties into "no plugin-level backend routes" above) — `calendar_auth`'s `CALENDAR_AUTH_PASSWORD_<LABEL>` keys are the existing example: set as a custom secret, read via `device_config.load_env_key(...)`.

## Dev environment

- `bash scripts/venv.sh` sets up `.venv/` from `install/requirements-dev.txt` (see macOS gotchas above for its own drift risk).
- **Dependabot's production-dependency entry targets `pyproject.toml`/`uv.lock` directly** (`package-ecosystem: "uv"`, `directory: "/"` — adopted from upstream `jtn0123/InkyPi#627`; previously a `pip` entry pointed at `/install` hand-edited the *generated* `install/requirements.in`/`requirements.txt`, silently drifting them from the real source of truth per `docs/dependency_locking.md`). Remaining gap: a merged uv-ecosystem PR still won't regenerate `install/requirements.txt` itself — `scripts/check_requirements_drift.sh` (runs in CI) fails until someone runs `uv export --format requirements.txt --no-dev --no-emit-project --output-file install/requirements.txt` and commits the result. `install/requirements-dev.txt` is unaffected (separate pip-compile pipeline, not part of this migration).
- `PYTHONPATH=src .venv/bin/python src/inkypi.py --dev` runs the dev server on port 8080 with a mock display, using `device_dev.json`. **Does not hot-reload** (served via `waitress`, not Flask's debug reloader) — restart after any code change. Plugin *code* is the exception: `plugin_registry.py` hot-reloads a plugin module on each `get_plugin_instance()` call in dev mode.
- This machine has no bare `python` on PATH, only `python3` (`which python` fails). Use `python3` for anything outside the venv, or `.venv/bin/python`/`.venv/bin/python3` inside it — both work there. `scripts/dev_watch.sh` already handles this correctly; follow its preference order in any new script.
- **Chromium/screenshot rendering**: `utils/image_utils.py` prefers Playwright (`_playwright_screenshot_html`, passes `executable_path` from the shared `_find_chromium_executable()` rather than letting Playwright resolve its own version-pinned bundled browser — that pin can silently mismatch what's actually downloaded in `~/Library/Caches/ms-playwright/`, in which case Playwright fails fast and *silently* falls back), falling back to a CLI subprocess (`take_screenshot`) if Playwright is unavailable or fails. Both backends share one resource-flag list (`_CHROMIUM_RESOURCE_FLAGS`/`_CHROMIUM_FILE_ACCESS_FLAGS`) — edit those, not each call site, when tuning Chromium flags. On macOS: install Playwright's `chrome-headless-shell` (`pip install playwright && playwright install chromium-headless-shell`), then put a **wrapper script** (not a symlink!) on `PATH` named `chromium-headless-shell` doing `exec "<real absolute path>" "$@"` — a symlink breaks because the binary resolves its resource directory from `argv[0]` without following symlinks (SIGTRAP).
- Render time for the Chrome-based custom plugins (calendar_auth, weather_de, abfahrtzeiten, regenalarm) is typically dominated by the network fetch, not the screenshot — measure the fetch and `render_image()` separately before assuming a slow plugin needs render-side optimization.
- **CSS build**: `src/static/styles/main.css` is *generated* — a concatenation of `partials/*.css` per `_imports.css`'s `@import` list. Edit the partials, not `main.css`. Rebuild with `python3 scripts/build_css.py` (`--minify` for production, `--check` for a dry-run). `scripts/dev_watch.sh` auto-rebuilds this (and JS, see below) on save under `styles/`/`scripts/`/`templates/` (needs `watchdog`: `pip install watchdog`).
- **JS/CSS production bundling**: `scripts/build_assets.py` bundles+minifies+content-hashes assets into `src/static/dist/` (gitignored), wired into `install/_common.sh::build_css_bundle()` (runs after `build_css.py`, both invoked by `install.sh`/`update.sh`) — so real installs get this automatically. Two JS bundles, not one — `common-sync.<hash>.min.js` (theme/csrf/client_errors, loaded without `defer`) and `common-deferred.<hash>.min.js` (the rest, `defer`'d) — matching `base.html`'s own sync/deferred script grouping exactly; collapsing them into one bundle would silently change the sync scripts' execution timing. `base.html`'s `{% if bundled_assets_enabled %}` (true when `dist/manifest.json` exists and is non-empty — `app_setup/asset_helpers.py`) picks the bundle over ~10 individual `<script>` tags. **If a new global script is added to `base.html`, add it to `JS_MANIFEST_SYNC` or `JS_MANIFEST_DEFERRED` in `build_assets.py` too** (whichever matches its `defer` attribute) — nothing currently catches this drifting other than `tests/test_asset_bundling.py`'s bundle-content assertions, which only check for the specific files known at the time they were written. Page-specific scripts (e.g. `plugin.html`'s `ui_helpers.js`, `settings.html`'s `dark_mode.js`) are not part of either bundle. `/static/dist/*` files get `Cache-Control: public, max-age=1yr, immutable` forced in `security_middleware.py::_apply_static_cache_headers` (safe only because every filename there is content-hashed); everything else under `/static/` keeps Flask's `no-cache` default deliberately, since non-hashed files (`main.css`, individual scripts) can change content without their URL changing. To locally test the bundled path: run `build_assets.py`, restart the dev server (the manifest is read once at startup, not per-request), and remove `src/static/dist/` afterward to go back to the normal (always-current) unbundled dev experience — `dev_watch.sh` doesn't keep the dist bundle in sync automatically.
- **Response compression**: `app_setup/compression.py`'s `apply_response_compression()` runs as the last step in `security_middleware.py`'s single after_request pipeline (must run last — it rewrites `Content-Length` and adds `Content-Encoding`/`Vary`). Gzip (stdlib, always on) by default; brotli instead when the client's `Accept-Encoding` allows it *and* the optional `brotli` package is importable (not a hard dependency — same "use it if present" pattern as `rjsmin`/Playwright elsewhere). Only compresses text-ish mimetypes (HTML/CSS/JS/JSON/SVG) above a small size floor — this alone excludes images/fonts (already binary-compressed, not worth the CPU) and SSE's `text/event-stream` (must never be buffered/compressed). `/static/dist/*` responses additionally cache their compressed bytes in-process keyed by path — bounded by construction, since a running process can only ever see the fixed, small set of dist paths its manifest was loaded with at startup.
- Waitress's thread pool (`_get_web_threads()` in `inkypi.py`) defaults to 2 in production (sized for a Pi Zero 2 W's RAM) but 8 in dev mode (`INKYPI_ENV=dev`/`--dev`) — `INKYPI_WEB_THREADS` overrides either explicitly. This matters because two things routinely hold a thread for a long time even with one user: the dashboard's SSE connection (`GET /api/events`, held open for the tab's lifetime) and any synchronous plugin render (`/preview_now`, `/update_now`, the on-demand `instance_image()` cache-fill). At 2 threads, one open dashboard tab plus one slow render leaves zero free — every other request just hangs until something frees up. Both SSE endpoints have a `max_subscribers` cap, but it's set far higher (50) than the thread count, so it doesn't protect against this.

## Notes on the ported plugins (abfahrtzeiten, calendar_auth, regenalarm, weather_de)

Originally built against the fatihak-based fork with custom `settings.html` pages, then ported onto this jtn0123 base — `generate_image()`/data-fetching logic is unchanged, but every settings page is now `build_settings_schema()` + widgets (enforced by this fork's test suite).

- **`abfahrtzeiten`**: departure board for German public transit (BVG/VBB/DB HAFAS-wrapper APIs, keyless, CORS-permissive). Prioritizes VBB/BVG inside a rough Berlin/Brandenburg bounding box, falls back to DB elsewhere. Per-stop fetch failures are isolated — only raises if every stop fails. Settings page: `abfahrtzeiten-stops` widget (address→nearby-stops→line/direction wizard). Entries are one JSON blob per stop (`entries[]`, 5 correlated fields) rather than parallel arrays, since they don't parallelize as cleanly as calendar's 2-field case. Result-list rendering uses DOM/`textContent`, not `innerHTML`, for untrusted API text.
- **`calendar_auth`** ("Calendar (with Login)"): clone of the built-in `calendar` plugin adding per-calendar HTTP Basic Auth. The password is never stored in plugin settings — only a per-entry credential *label*, used to look up `CALENDAR_AUTH_PASSWORD_<LABEL>` via the custom-secrets mechanism. This split exists because the settings-page route re-embeds a plugin instance's entire stored settings as JSON on every edit — anything in the entries list round-trips to the browser in plaintext, so the password can't live there. Settings page: `calendar-auth-repeater` widget, storage as parallel bracket-arrays (`calendarAuthURLs[]`/`Colors[]`/`Usernames[]`/`Labels[]`).
- **`regenalarm`**: German rain radar dashboard for a single location (reverse-engineered `regenonline.de` binary protocol; `_regenalarm/` at repo root is scratch research material, unused at runtime). Renders via HTML/CSS/Chrome, not Pillow — panel sizing is computed in Python as literal pixel values (`_layout_px()`) because the in-use `chrome-headless-shell` build has a compositor bug where content inside a box sized via a dynamic CSS unit (`dvh`/`%`/flex-grow) paints at some unrelated fixed size despite correct layout (`getBoundingClientRect()` confirms it) — giving the box a literal `px` dimension is the only known fix. Settings page reuses `weather-map` with a central-Germany default location. Upstream data refreshes ~every 15 minutes — don't set the playlist interval below that.
- **`weather_de`** ("Weather (Germany)"): clone of the built-in `weather` plugin adding a third provider, **Bright Sky** (`api.brightsky.dev`, free/keyless DWD wrapper) — no sunrise/sunset/UV/AQI/feels-like from Bright Sky itself, so sunrise/sunset come from `astral`, UV/AQI reuse Open-Meteo's air-quality endpoint, feels-like falls back to actual temperature. Also has an `openMeteoModel` setting to pin Open-Meteo to DWD's ICON-D2 model (higher resolution over Germany, no `precipitation_probability` since it's a deterministic run — parsing is null-safe for that). Carries the 8-language localization feature from upstream fatihak PR #670, not present in jtn0123's own `weather` plugin. Its OpenWeatherMap key is only actually required when that provider is selected (see the `api_key_required_for_settings()` hook above).
