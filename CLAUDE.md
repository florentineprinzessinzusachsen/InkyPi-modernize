# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Repo context — read this first

- This is a **private fork of `jtn0123/InkyPi`** (itself a heavily-diverged fork of the original `fatihak/InkyPi`, ~1400 commits ahead). `origin` is the private repo (`florentineprinzessinzusachsen/InkyPi-jtn0123`) — real commits and pushes happen here. `upstream` (jtn0123, push-disabled) is kept for pulling future updates.
- A prior private fork based directly on `fatihak/InkyPi` still exists as the `fatihak-fork-origin` remote / `fatihak-main` local branch, kept as a reference/backup — not the active line of work.
- **Avoid modifying core InkyPi application code where a plugin-local alternative exists.** Most plugin logic (`src/plugins/<plugin_id>/<plugin_id>.py`, its `render/`, its Python) stays self-contained. **Exception, specific to this fork:** the settings-page system (see below) is schema-driven, and any settings-page widget needing genuinely new interactivity (not just a new field type) has no plugin-local mechanism — it requires additions to the shared `src/static/scripts/plugin_schema.js` and a new file in `src/templates/widgets/`. That's an accepted, narrow exception; it does not extend to other core files (`src/inkypi.py`, `src/blueprints/*.py` route logic, `src/refresh_task/`, etc.) without flagging it first.
- `.gitignore` and other repo-hygiene/tooling files are fine to touch when asked.

## Mistakes made in earlier sessions (don't repeat these)

1. **Running the full test suite proactively, unprompted.** This fork's suite is ~5000 tests and takes ~3 minutes per run. Ran it after nearly every change in one session (after each merged PR, each plugin port, each bug fix) without being asked — it adds up fast. **Rule: only run the test suite (full or scoped) when the user explicitly asks for it.** If a change needs verifying, prefer something narrow — a single test file, a targeted manual check via the dev server, or just a compile/syntax check — over the full suite, unless told otherwise.
2. **Blind `git checkout -- <file>` on a file that is also live runtime state.** In the old fatihak-based fork, `src/config/device_dev.json` was both git-tracked *and* the live storage for dev-mode playlists/settings, so `git checkout --` on it silently destroyed accumulated settings. **In this jtn0123-based fork the convention is different**: `src/config/device_dev.json` is a small, intentionally-clean *checked-in dev fixture* (not gitignored) — it's fine as tracked content, but manual testing/dev-server use can dirty it with real playlist/instance data. Check `git status` on it after any dev-server session and don't commit test noise into it; don't assume either repo's convention applies to the other without checking `git ls-tree`/`.gitignore` first.
3. **Killing a process without checking whose it was.** Always `lsof -i :<port>` and check what a bound port actually is before killing it — don't assume. Once confirmed as this project's own dev server (e.g. `src/inkypi.py --dev`), it's fine to restart it yourself when needed (e.g. to pick up code changes, since it doesn't hot-reload) without asking each time.
4. **Adding a backend Flask blueprint for a plugin's settings-page needs.** Unnecessary in both forks: if a settings-page wizard needs live external data (autocomplete, lookups), check whether the external API sends `Access-Control-Allow-Origin: *` first (`curl -i <url> -H "Origin: http://localhost:8080"`) — public read-only APIs very often do, and calling them directly from the settings-page's client-side JS avoids a backend route entirely. Abfahrtzeiten's address/stop/line wizard works this way against the BVG/VBB/DB transit APIs.
5. **Testing artifacts leaking into git status.** Manual verification (forcing plugin refreshes, running the dev server) writes to `src/static/images/current_image.png` and can dirty `src/config/device_dev.json` (see #2). Clean these up after verification, but *diff first* — don't reflexively revert/delete without checking the change is actually just test noise.
6. **Over-testing every edge case with screenshots.** The user tests visually themselves and is faster at it than a screenshot-render-read loop — and that loop has a real error rate. Don't proactively render every stop-count/resolution/orientation/data-scenario combination after a change. Do a quick sanity check (runs without error, the core case looks right) and stop there; let the user report back if something's off. Reserve a closer look for genuinely new logic (a new algorithm with real branches), and even then prefer a targeted check (a one-off print of computed values) over a screenshot sweep.

## macOS dev-environment gotchas found in jtn0123's own code (not our bugs, but bit us)

- **Plugin subprocess execution can SIGSEGV on macOS.** Plugins render in an isolated subprocess (`src/refresh_task/executor.py` + `worker.py`) for crash isolation. `worker.py::_get_mp_context()` used to prefer `fork` on any non-Linux platform. Forking this app's always-multi-threaded parent (waitress worker threads + the refresh_task background thread) is unsafe: if a plugin's first post-fork action touches a non-fork-safe macOS framework (any `requests`/`urllib` call triggers proxy autodetection via `_scproxy` → CoreFoundation/SystemConfiguration), the child can inherit a broken lock and crash with SIGSEGV. Confirmed via an actual macOS crash report (`~/Library/Logs/DiagnosticReports/Python-*.ips`). Non-deterministic (thread-timing dependent) — a minimal single-threaded repro script did *not* reproduce it, only the real app did. **Fixed**: `_get_mp_context()` now prefers `spawn` over `fork` on non-Linux. Linux (the real Pi target) is untouched — still `forkserver`/`fork`, unaffected either way since this crash class doesn't exist there.
- **OSM map tiles 403 "Access Blocked" in the location-picker widget.** The app sets `Referrer-Policy: no-referrer` on every response (`security_middleware.py`). That means the Leaflet map in the `weather-map` widget sends zero Referer when fetching OpenStreetMap tiles, and OSM's tile usage policy rejects that. **Fixed**: `/plugin/<plugin_id>` (the settings-page route) now explicitly overrides to `Referrer-Policy: strict-origin-when-cross-origin` on its own response only — sends just the origin cross-origin, satisfies OSM's policy, leaves the app-wide stricter default untouched everywhere else.
- **`install/requirements-dev.txt` can silently drift from `install/requirements.txt`.** Two separate pipelines: `requirements.txt` is uv-generated from `pyproject.toml` (checked by `scripts/check_requirements_drift.sh`); `requirements-dev.txt` is pip-compiled from a *manually maintained* duplicate list in `requirements-dev.in` (comment: "keep in sync with requirements.in") — not checked by that script. Found `prometheus-client` missing from it, breaking `tests/unit/test_metrics.py` on a fresh `scripts/venv.sh` setup. Fix by hand-adding the missing entry to `requirements-dev.txt` at the right alphabetical spot with a real hash (queryable via a local `pip-compile` run) — **don't just regenerate the whole file via `pip-compile` on macOS**: it silently drops `sys_platform == "linux"`-gated entries (e.g. `memray` and its dependency chain) that a Linux-compiled version correctly preserves, since pip-compile (unlike `uv`'s universal lockfiles) doesn't resolve cross-platform markers properly.

## InkyPi plugin architecture (what actually matters, jtn0123 base)

- **Contract:** `src/plugins/<id>/<id>.py` defines a class extending `BasePlugin` (`src/plugins/base_plugin/base_plugin.py`), implementing `generate_image(self, settings, device_config) -> PIL.Image`. Raise `RuntimeError` with a clear message on unrecoverable failure — surfaced to the user. Same as upstream fatihak in spirit; the base class itself has been heavily modernized (type hints, `Protocol`-typed `device_config`, `PLUGIN_API_VERSION`) but `generate_image`/`render_image`/`get_plugin_dir`/`generate_settings_template` call signatures are unchanged.
- **`plugin-info.json`** wants `{display_name, id, class, api_version, version}` — `api_version`/`version` are optional/backward-compatible (missing just logs a notice in `plugin_registry.py`), but add them for parity with built-in plugins.
- **Settings pages are schema-driven — this is enforced, not optional.** `tests/unit/test_legacy_settings_cleanup.py` fails the build if any plugin (other than `base_plugin`/`year_progress`, explicitly exempted) lacks a `build_settings_schema()` override, or if any plugin directory (other than `base_plugin`) contains a `settings.html`. The old fatihak-style "custom `settings.html` + inline JS" pattern is dead here even though `plugin.html` technically still has a fallback include path for it.
  - DSL lives in `plugins.base_plugin.settings_schema`: `schema(*sections)`, `section(title, *items)`, `row(*fields)`, `field(name, type, label=..., options=..., visible_if={...}, ...)`, `option(value, label)`, `option_group(label, *options)`, `callout(text, tone=...)`, `widget(widget_type, template=..., config={...})`.
  - Field types: `text`/`url`/`number`/etc (plain input), `checkbox` (needs `submit_unchecked`/`checked_value`/`unchecked_value` to actually submit a value when unchecked), `radio_segment`, `select` (supports `options_by_value` for one field's options depending on another's value), `color`, `textarea`, `hidden`.
  - `visible_if={"field": name, "equals"|"operator": ...}` is single-field only — no compound AND/OR conditions. Design around that (e.g. a field that should show under multiple unrelated conditions may need to just always show, accepting a minor UX simplification).
  - **Widgets** are for anything a field type can't express (maps, repeaters, live external lookups). A widget = a template in `src/templates/widgets/<name>.html` (rendered via `{% include item.template %}`, gets `plugin_settings` in scope) + a JS init function registered in `src/static/scripts/plugin_schema.js`'s `widgetInitializers` map (keyed by the `widget_type` string), called as `init(widgetElement, config)` where `config` is the plugin's saved settings merged with any static `config=` passed to `widget()`. Existing reusable ones: `weather-map` (single lat/long picker — reuse as-is for any plugin needing one location), `calendar-repeater` (multi-entry list with parallel bracket-arrays, e.g. `calendarURLs[]`/`calendarColors[]` — the convention for new multi-entry lists, cleaner than JSON-blob-per-row when fields parallelize cleanly). Modals inside a widget manage their own show/hide directly (`hidden` attribute + `style.display` + a CSS class) — there's no global `openModal()`/`closeModal()` to rely on.
  - `foo[]` fields still auto-collect into a Python list via `parse_form()`'s `request_form.getlist` — unchanged from upstream fatihak.
- **Timezones: `zoneinfo`, not `pytz`.** `pytz` isn't a dependency in this fork. Use `from utils.time_utils import get_timezone` (`get_timezone(tz_name) -> tzinfo`, falls back to UTC on invalid input) wherever a plugin needs to turn a timezone-name string into a tzinfo object.
- **`device_config`**: `.get_resolution()`, `.get_config(key, default)`, `.load_env_key(name)` for API keys — unchanged. Declare a required key via `template_params['api_key'] = {"required": True, "service": ..., "expected_key": "ENV_VAR_NAME"}` in `generate_settings_template()`; entered through the generic `/api-keys` UI, never a custom form.
- **No plugin-level backend routes** — same constraint as upstream fatihak, same workaround (direct client-side `fetch()` against CORS-permissive external APIs).
- **Plugins render in an isolated subprocess** (`src/refresh_task/executor.py`/`worker.py`), not in-process, for crash isolation — see the macOS fork/spawn gotcha above if touching that area.
- **CSRF**: session-cookie-based token, required on all non-safe-method requests except a short exempt list. Token available via the `csrf-token` meta tag in `base.html`, or `{{ csrf_token() }}` in a form. Relevant when scripting requests (e.g. curl) against `/update_now` or other POST routes for testing — GET a page first to establish the session + grab the token.
- **`/__smoke/render`**: an opt-in, CSRF-exempt endpoint (only registered when `INKYPI_SMOKE_FORCE_RENDER=1` is set at process start) that calls `plugin.generate_image({}, device_config)` directly in-process — no subprocess, doesn't push to the display. Useful for a quick check that a plugin's render logic runs at all, but does *not* exercise the real subprocess/fork-or-spawn path, so it wouldn't have caught the macOS SIGSEGV above.

## Dev environment notes

- `bash scripts/venv.sh` sets up `.venv/` from `install/requirements-dev.txt` (see the drift gotcha above — it can be missing something `pyproject.toml` actually declares).
- `PYTHONPATH=src .venv/bin/python src/inkypi.py --dev` runs the dev server on port 8080 with a mock display, using `src/config/device_dev.json` (tracked dev fixture in this fork — see mistake #2 above).
- **The dev server does not hot-reload.** Served via `waitress`, not Flask's debug reloader — `kill` and restart after any code change before testing, or you'll silently test stale code.
- **Chromium/screenshot setup on macOS is fragile.** `_find_chromium_binary()` (`src/utils/image_utils.py`) does `shutil.which()` for `chromium-headless-shell`/`chromium`/`chrome`. Homebrew's `chromium` cask is deprecated. Working setup: install Playwright's `chrome-headless-shell` (`pip install playwright && playwright install chromium-headless-shell`), then put a **wrapper script** (not a symlink!) on `PATH` named `chromium-headless-shell` that does `exec "<real absolute path>" "$@"` — a plain symlink breaks because the binary resolves its resource directory from `argv[0]` without following symlinks, crashing with SIGTRAP when invoked through one.

## Notes on the ported plugins (abfahrtzeiten, calendar_auth, regenalarm, weather_de)

Originally built against the fatihak-based fork with custom `settings.html` pages, then ported onto this jtn0123 base — the `generate_image()`/data-fetching logic is unchanged, but every settings page was rewritten to `build_settings_schema()` + widgets (see architecture section above) since the old approach is actively forbidden by this fork's test suite.

- **`abfahrtzeiten`**: departure board for German public transit (BVG/VBB/DB HAFAS-wrapper APIs, keyless, CORS-permissive). Prioritizes VBB/BVG inside a rough Berlin/Brandenburg bounding box, falls back to DB elsewhere. Per-stop fetch failures are isolated; only raises if *every* stop fails. Settings page: a new `abfahrtzeiten-stops` widget (`src/templates/widgets/abfahrtzeiten_stops.html` + `initAbfahrtzeitenStops` in `plugin_schema.js`) ports the address→nearby-stops→line/direction wizard. Entries stay one JSON blob per stop (`entries[]`, 5 correlated fields: provider/stopId/stopName/lineName/direction) rather than parallel arrays — doesn't parallelize as cleanly as calendar's 2-field case. Result-list rendering uses DOM/`textContent` construction, not `innerHTML` string interpolation of untrusted API text (an XSS-prone pattern from the original port, fixed while porting, consistent with this fork's more security-conscious posture elsewhere).
- **`calendar_auth`** ("Calendar (with Login)"): clone of the built-in `calendar` plugin adding per-calendar HTTP Basic Auth for ICS feeds requiring login. Password is deliberately never stored in plugin settings — only a per-entry credential *label*, used to look up `CALENDAR_AUTH_PASSWORD_<LABEL>` via the existing `/api-keys`/env-key mechanism. This split is deliberate (settings-page routes re-embed a plugin instance's entire stored settings as JSON on every edit, so anything in the entries list would round-trip to the browser in plaintext) — don't simplify it back to storing passwords directly without checking first. Settings page: new `calendar-auth-repeater` widget, modeled on the built-in calendar plugin's own `calendar-repeater`; storage switched from one JSON blob per row to parallel bracket-arrays (`calendarAuthURLs[]`/`Colors[]`/`Usernames[]`/`Labels[]`) to match that convention.
- **`regenalarm`**: German rain radar dashboard for a single location (reverse-engineered `regenonline.de` binary protocol client; `_regenalarm/` at the repo root is scratch research material, not used at runtime). Renders via HTML/CSS/Chrome, not Pillow — panel sizing is computed in Python as literal pixel values (`_layout_px()`) because the `chrome-headless-shell` build in use has a compositor bug where painted image/SVG/background-image content inside a box sized via a dynamic CSS unit (`dvh`/`%`/flex-grow) renders at some unrelated fixed size, even though the box's layout is confirmed correct via `getBoundingClientRect()`. Only fix found: give that element's own box a literal `px` dimension. Settings page: reuses the existing `weather-map` widget as-is, with `config={"latitude": "51.1657", "longitude": "10.4515"}` to default new instances to central Germany instead of the widget's built-in NYC default. Upstream data refreshes ~every 15 minutes — don't set the playlist refresh interval below that.
- **`weather_de`** ("Weather (Germany)"): clone of the built-in `weather` plugin adding (1) a third provider, **Bright Sky** (`api.brightsky.dev`, free/keyless DWD wrapper — real SYNOP observations + MOSMIX forecast model); no sunrise/sunset/UV/AQI/feels-like from Bright Sky itself, so sunrise/sunset come from `astral`, UV/AQI reuse the Open-Meteo air-quality endpoint, feels-like falls back to actual temperature. (2) An `openMeteoModel` setting to pin Open-Meteo to DWD's ICON-D2 model (`icon_d2`, higher resolution over Germany, ~2-day horizon, no `precipitation_probability` field at all since it's a deterministic run not an ensemble — forecast/hourly parsing is null-safe for this). Also carries the localization feature ported from upstream fatihak PR #670 (8-language `LOCALE_DATA`, translated labels, localized dates) — not present in jtn0123's own `weather` plugin. Settings page: reuses the `weather-map` widget as-is (same NYC-default behavior as the original `weather` plugin).
