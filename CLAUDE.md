# CLAUDE.md

Guidance for Claude Code when working in this repository. This file is a reference for conventions, architecture, and APIs — not a changelog. Keep entries here durable and forward-looking; don't record dates, "fixed on X", or debugging narratives.

## Repo context

- `origin` (private, real commits/pushes) is `florentineprinzessinzusachsen/InkyPi-modernize` — GitHub redirects the old `InkyPi-jtn0123` URL, but resolve remotes to the new name rather than relying on that. `upstream` (jtn0123, push-disabled) is for pulling updates — check `git log main..upstream/main` occasionally and `git cherry-pick` relevant commits (`--no-commit -n` to preview first). `fatihak-fork-origin`/`fatihak-main` is an older private fork, kept only as reference.
- **`gh` has no default repo**, and with four remotes, a bare `gh pr view`/`gh pr list` can silently resolve against the wrong one with no error. Run `gh repo set-default florentineprinzessinzusachsen/InkyPi-modernize` once per environment, or pass `--repo` explicitly, before trusting `gh pr`/`gh issue` output.
- **Avoid modifying core InkyPi code where a plugin-local alternative exists** — most plugin logic (`src/plugins/<id>/<id>.py`, its `render/`) stays self-contained. Exception: a settings-page widget needing new interactivity requires shared `src/static/scripts/plugin_schema.js` + a new `src/templates/widgets/` file — the only accepted core-file exception. Flag any other core change (`src/inkypi.py`, `src/blueprints/*.py`, `src/refresh_task/`) first.

## Dependabot / branch maintenance

- **A dependabot PR's branch can look alive (or dead) when it isn't.** Run `git remote prune origin` before trusting `git branch -r`. A branch with no PR in `gh pr list --search` may still have one (that endpoint misses matches) — confirm via `gh api repos/<owner>/<repo>/pulls?state=all&head=<owner>:<branch>` before deleting.
- **When a dependabot PR won't auto-rebase** after `@dependabot rebase`, resolve it yourself: fetch it (`git fetch origin pull/<N>/head:<branch>`), merge `main` into it inside an isolated `git worktree` (never the main checkout if it has uncommitted work), resolve conflicts, fast-forward local `main` to the merge commit, push, then close the PR referencing the commit.
- **Check a tool's actually-installed version before touching its config schema** — an in-flight PR isn't proof a bump landed. E.g. `[tool.mutmut]` uses 3.x key names (`source_paths` etc — `paths_to_mutate`/`tests_dir`/`runner`/`dict_synonyms` are 2.x and gone) because `install/requirements-dev.txt` pins `mutmut==3.6.0`.
- **`uv lock` doesn't float an already-satisfied range to latest** — it keeps resolutions stable. To pick up a newer version within an existing range (e.g. `numpy>=2.0,<3`), run `uv lock --upgrade-package <name>`; a bare `uv lock` only reacts to a changed constraint.

## Working conventions

- **Once a change is tested and confirmed working, commit, push, and deploy without waiting to be asked.** Commit at each verified milestone, push to `origin main`, then if `frame` is reachable (`ssh -o ConnectTimeout=3 -o BatchMode=yes frame true`), deploy with the sequence below. If `frame` isn't reachable, still commit and push, skip deploy. Overrides the general ask-before-push/deploy default for this repo.
  - **`main.css` always locally diverges from git before you can pull — this is expected, not damage.** `install.sh`/`update.sh` (`build_css_bundle()` in `install/_common.sh`) run `build_css.py --minify`, which overwrites the git-tracked `src/static/styles/main.css` **in place** with a minified rebuild. That happens on every install/update, so the working tree on `frame` is never clean relative to git's unminified, formatted version — a bare `git pull` reliably fails with "local changes would be overwritten". `install/do_update.sh` already works around this (`git checkout -- src/static/styles/main.css` before every checkout); do the same manually:
    ```bash
    sudo git -C /opt/InkyPi checkout -- src/static/styles/main.css
    sudo git -C /opt/InkyPi pull
    ```
  - **A `git pull` alone does not update what the browser actually receives.** `base.html` serves the hash-named bundle in `src/static/dist/` (gitignored, built by `build_assets.py` from the *just-rebuilt* `main.css`) instead of `main.css`/individual `<script>` tags whenever `dist/manifest.json` exists — which it does on any installed Pi. Skipping the rebuild silently leaves the live site on old CSS/JS after a pull that touched `src/static/styles/partials/*.css` or `src/static/scripts/*.js`, even though templates (server-rendered per request) update immediately. Rebuild both, then restart:
    ```bash
    sudo /usr/local/inkypi/venv_inkypi/bin/python /opt/InkyPi/scripts/build/build_css.py --minify
    sudo /usr/local/inkypi/venv_inkypi/bin/python /opt/InkyPi/scripts/build/build_assets.py
    sudo systemctl restart inkypi.service
    ```
    Confirm `active`/`running`, and that `curl -s http://frame/ | grep -o 'common\.[a-f0-9]*\.min\.css'` shows a new hash if CSS changed.
  - This lightweight path (pull + rebuild bundle + restart) is for iterating on `main` — it skips `update.sh`'s apt/pip/dependency-sync machinery. If a change touched Python dependencies (`pyproject.toml`, `install/requirements*.in`) or install/update scripts themselves, use the real update path instead: `sudo INKYPI_UPDATE_CHANNEL=edge bash /opt/InkyPi/install/do_update.sh` — it fetches, resets hard to `origin/main`, then runs the full `update.sh` (deps + CSS/asset bundle + restart) for you. Slower (dependency install), but it's the one path proven to leave `frame` fully in sync.
  - **Port numbers differ: dev server is `:8080`, the deployed Pi serves on `:80`** (waitress, per `journalctl -u inkypi`). Don't reuse a `localhost:8080` check against `frame`.
- Only run the test suite when explicitly asked. For verifying a change, prefer something narrow — a single test file, a manual dev-server check, or a compile/syntax check.
- `src/config/device_dev.json` and `src/static/images/current_image.png` are gitignored — dev-server use writes to both freely, no need to diff or revert them.
- Always `lsof -i :<port>` before killing a bound process. Restarting this project's own dev server yourself after a code change needs no confirmation.
- Don't add a backend Flask blueprint for a plugin's settings-page data needs (see plugin architecture below) — check the external API for `Access-Control-Allow-Origin: *` (`curl -i <url> -H "Origin: http://localhost:8080"`) and call it directly from client-side JS.
- Don't over-test with screenshots — the user tests visually, faster than a screenshot loop. Do a quick sanity check and stop; ask the user for feedback instead of iterating on screenshots yourself.

## macOS dev-environment gotchas

- **Plugin subprocess execution can SIGSEGV on macOS** if forked from this app's multi-threaded parent — a post-fork `requests`/`urllib` call hits macOS's non-fork-safe proxy autodetection (`_scproxy`). `worker.py::_get_mp_context()` uses `spawn` on non-Linux for this; Linux (the real Pi target) keeps `forkserver`/`fork`.
- `security_middleware.py` sets `Referrer-Policy: no-referrer` globally, which breaks the Leaflet map in the `weather-map` widget (OSM rejects no-Referer tile requests). `/plugin/<plugin_id>` overrides to `strict-origin-when-cross-origin` on its own response.
- `install/requirements-dev.txt` is pip-compiled from a manually maintained `requirements-dev.in` — nothing checks they stay in sync. Regenerating via `pip-compile` on macOS **drops every `sys_platform == "linux"`-gated entry** (e.g. `memray`). Verify by grepping the output for `sys_platform` and diff the count against `requirements-dev.in`; restore any dropped entry's hash block from git history.

## Waveshare display driver (`src/display/waveshare_epd/epdconfig.py`)

- **`RaspberryPi.digital_write()`/`digital_read()` must handle `CS_PIN`.** SPI chip-select is driven manually via GPIO (`GPIO_CS_PIN`, `self.SPI.no_cs = True`), not left to `spidev`'s automatic hardware CS. Automatic CS doesn't reliably frame transfers on the epd7in3e/Pi Zero 2 W combo: the panel silently never receives valid commands (BUSY never asserts, no exception anywhere). Don't reintroduce automatic CS.
- **Symptom of broken CS framing:** `ReadBusyH()` returns instantly, so `Clear()`+`display()` finishes in seconds instead of the ~15-30s a real full refresh takes. GPIO-backend or pull-resistor changes won't fix this — the cause is CS framing, not the GPIO stack.
- **`epd7in3e.py`'s `0x30` command** (right after the booster soft-start block in `init()`) controls refresh speed — undocumented by Waveshare. Shipped value is `0x07` (fastest before color quality degrades at `0x08`+); re-test full-panel color quality before changing it. This file is a git-tracked, intentionally-modified copy of the pinned upstream driver — `install/waveshare-manifest.txt` still lists the original upstream hash (same as `epdconfig.py`'s row), and `install.sh` never re-fetches over an existing file, so the modification survives installs/updates. Don't try to make the manifest hash match this file — that defeats its purpose for genuinely-pristine drivers.
- **No vendor fast-refresh mode exists** for this or any color/grayscale Waveshare panel — `EPD_7IN3E_Init_Fast()` is declared but never implemented anywhere in Waveshare's demo repo (only pure monochrome panels have a real `Init_Fast`). Don't go looking for one.

## InkyPi plugin architecture

- **Contract:** `src/plugins/<id>/<id>.py` defines a class extending `BasePlugin` (`src/plugins/base_plugin/base_plugin.py`), implementing `generate_image(self, settings, device_config) -> PIL.Image`. Raise `RuntimeError` with a clear message on unrecoverable failure — surfaced to the user.
- **`plugin-info.json`** needs `{display_name, id, class, api_version, version}` — `api_version`/`version` are optional but include them for parity with built-in plugins.
- **Settings pages are schema-driven and enforced:** `tests/unit/test_legacy_settings_cleanup.py` fails the build if a plugin (other than `base_plugin`/`year_progress`) lacks `build_settings_schema()` or has a `settings.html`.
  - DSL lives in `plugins.base_plugin.settings_schema`: `schema(*sections)`, `section(title, *items)`, `row(*fields)`, `field(name, type, label=..., options=..., visible_if={...}, ...)`, `option(value, label)`, `option_group(label, *options)`, `callout(text, tone=...)`, `widget(widget_type, template=..., config={...})`.
  - Field types: `text`/`url`/`number`/etc, `checkbox` (needs `submit_unchecked`/`checked_value`/`unchecked_value` to submit a value when unchecked), `radio_segment`, `select` (supports `options_by_value`), `color`, `textarea`, `hidden`.
  - `visible_if={"field": name, "equals"|"operator": ...}` is single-field only — no compound AND/OR. A field needing multiple conditions may just need to always show.
  - **Widgets** handle anything a field type can't (maps, repeaters, live external lookups): a template in `src/templates/widgets/<name>.html` (via `{% include item.template %}`, gets `plugin_settings` in scope) + a JS init function in `plugin_schema.js`'s `widgetInitializers` map (`init(widgetElement, config)`). Reusable: `weather-map` (lat/long picker), `calendar-repeater` (parallel bracket-arrays like `calendarURLs[]`/`calendarColors[]` — use this when fields parallelize cleanly; otherwise one JSON blob per row, e.g. `abfahrtzeiten`'s 5-field entries). Modals inside a widget manage their own show/hide (`hidden` + `style.display` + a class) — no global `openModal()`/`closeModal()`.
  - `foo[]` fields auto-collect into a Python list via `parse_form()`'s `request_form.getlist`.
  - **Plugin icons are SVG-only** — every plugin resolves through `PLUGIN_ICON_MAP` in `templates/macros/icons.html` (a Phosphor icon name per plugin id; falls back to a generic icon if absent). There is no per-plugin `icon.png`/raster fallback — that scheme (and its `img.icon-image`/`img.app-icon` dark-mode backing-plate CSS in `_plugins.css`) was removed. A new plugin's icon means adding a `PLUGIN_ICON_MAP` entry, which is a core-template edit.
  - A plugin can implement `api_key_required_for_settings(self, settings) -> bool` to make its `api_key` requirement conditional on another setting — `blueprints/plugin.py::plugin_page()` calls it once real settings are known. Only affects page-load evaluation (correct after save+reload), not live reactivity to an unsaved dropdown change.
- **Timezones: `zoneinfo`, not `pytz`** (not a dependency here). Use `utils.time_utils.get_timezone(tz_name) -> tzinfo` (falls back to UTC on invalid input).
- **`device_config`**: `.get_resolution()`, `.get_config(key, default)`, `.load_env_key(name)`. Declare a required API key via `template_params['api_key'] = {"required": True, "service": ..., "expected_key": "ENV_VAR_NAME"}` in `generate_settings_template()` — entered through `/settings/api-keys`, never a custom form.
- **No plugin-level backend routes** — use direct client-side `fetch()` against CORS-permissive external APIs instead.
- **Plugins render in an isolated subprocess** (`refresh_task/executor.py`/`worker.py`) for crash isolation. Only the rendered image crosses back (via a tempfile path) — any other mutation `execute()` makes on a passed-in object (e.g. setting `plugin_instance.latest_refresh_time`) happens on that process's own copy and is lost. Replicate needed state changes in the parent process instead (`task.py::_perform_refresh()`, after `_execute_with_policy()` succeeds).
- **CSRF**: session-cookie-based token, required on all non-safe-method requests except a short exempt list. Token via the `csrf-token` meta tag in `base.html`, or `{{ csrf_token() }}` in a form. When scripting POST requests (curl), GET a page first to establish the session and grab the token.
- **`/preview_now` (POST) + `/preview_now_image/<plugin_id>` (GET)**: renders from submitted form settings, writes a scratch PNG (`plugin_image_dir/_preview_scratch_<plugin_id>.png`) — no display push, no history, no persisted settings. This is the settings page's Preview button. **`/update_now`** also pushes to the real/mock display, records history, and updates `refresh_info` — a real refresh. Use `/preview_now` for anything that should be look-but-don't-touch.
- **`/__smoke/render`**: opt-in (`INKYPI_SMOKE_FORCE_RENDER=1`), CSRF-exempt, calls `plugin.generate_image({}, device_config)` in-process — no subprocess, no display push. Confirms a plugin's render logic runs at all, but empty settings can't exercise real instance config.
- **To check a real instance's render directly:** in a one-off script, `INKYPI_ENV=dev` + `config.Config()` + `plugins.plugin_registry.get_plugin_instance(device_config.get_plugin(plugin_id))`, pull real settings from `device_config.get_config('playlist_config')['playlists'][...]['plugins'][...]['plugin_settings']`, call `plugin.generate_image(settings, device_config)` directly — skips browser/refresh_task/subprocess. Blank-render check: `np.array(image.convert('RGB')).mean()` — 255 means solid white.
- **HTML-render plugin templates using `{{static_dir}}`** need `generate_image()` to set `template_params["static_dir"] = self.to_file_url(resolve_path("static"))` before `render_image()` — the Jinja env (`self.env`) has no Flask `static_dir`/`url_for` global. Missing this silently produces a 100%-blank image with no Python error (the failure is a browser-side `ReferenceError` inside headless Chromium). `calendar.py`/`calendar_auth.py` set it; `weather.py`'s `chart.js` reference does not.
- **Multi-URL/multi-provider plugin fetches should be concurrent** via `concurrent.futures.ThreadPoolExecutor`, not a sequential loop. Use `.map()` when every item fetches the same way and any failure should abort the batch (`calendar.py`); `.submit()`/`.result()` per call for a small fixed set of different calls (`weather_de`'s per-provider branches); a try/except inside the worker when per-item failure isolation matters (`abfahrtzeiten`'s per-stop case). Cap `max_workers` (e.g. `min(len(items), 8)`). Use `utils.http_client.get_http_session()` (pooled, retries) instead of bare `requests`.

## Frontend / dark-mode design-system conventions

- Dark-mode UI borders (`--surface-border`/`--panel-border`/`--border-strong` in `_tokens.css`) need roughly **3:1 contrast** against `--surface` (WCAG's non-text minimum) — much lower is effectively invisible. `panel-border` should equal `surface-border` unless there's a specific reason not to; keep both in sync across all three aesthetics (console/paper/minimal).
- `.icon-button` is a large-square-tile primitive (`height: 90px`, `aspect-ratio: 1`, for grid icon-picker tiles) — reusing it elsewhere (e.g. a repeater row's remove button) inherits that sizing and, combined with `align-items: stretch`, can stretch sibling inputs to match. `.compact-repeater-toolbar .remove-btn` overrides this to 44px for the calendar/calendar_auth/todo_list widgets — watch for the same trap elsewhere.
- The plugin settings page's Preview card is a single full-width image (`.status-bar` in `_preview.css` is one column) — no side-by-side comparison card.

## API keys / custom secrets

- `/settings/api-keys` (GET, `settings.api_keys_page` in `blueprints/settings/_config.py`) is the only API-keys page — renders the 6 fixed provider cards (`_FIXED_PROVIDER_KEYS`) and a "Custom secrets" section for everything else in `.env`, via the same `api_key_card` macro for both.
- Saving: `POST /settings/save_api_keys` handles both fixed and custom keys in one request — any submitted field matching `_CUSTOM_KEY_NAME_RE` (`^[A-Za-z_][A-Za-z0-9_]*$`) that isn't a fixed or internal key gets written via `device_config.set_env_key()`. Deleting: `POST /settings/delete_api_key`, same validation.
- Any plugin needing a per-instance or arbitrary secret should use this mechanism (see "no plugin-level backend routes" above) — `calendar_auth`'s `CALENDAR_AUTH_PASSWORD_<LABEL>` keys are the example: set as a custom secret, read via `device_config.load_env_key(...)`.

## Dev environment

- `bash scripts/dev/venv.sh` sets up `.venv/` from `install/requirements-dev.txt` (drift risk: see macOS gotchas above).
- **Dependabot's production-dependency entry targets `pyproject.toml`/`uv.lock` directly** (`package-ecosystem: "uv"`). A merged PR still won't regenerate `install/requirements.txt` — `scripts/checks/check_requirements_drift.sh` (CI) fails until someone runs `uv export --format requirements.txt --no-dev --no-emit-project --output-file install/requirements.txt` and commits it. `install/requirements-dev.txt` is a separate, unaffected pip-compile pipeline.
- `PYTHONPATH=src .venv/bin/python src/inkypi.py --dev` runs the dev server on port 8080 with a mock display, using `device_dev.json`. **Does not hot-reload** (waitress, not Flask's debug reloader) — restart after any code change. Exception: `plugin_registry.py` hot-reloads plugin code on each `get_plugin_instance()` call in dev mode.
- No bare `python` on this machine, only `python3`. Use `python3` outside the venv, `.venv/bin/python`(3) inside it. `scripts/dev/dev_watch.sh` follows this — match it in any new script.
- **Chromium/screenshot rendering**: `utils/image_utils.py` prefers Playwright (`_playwright_screenshot_html`, via the shared `_find_chromium_executable()`), falling back to a CLI subprocess if Playwright is unavailable or fails. Both share one resource-flag list (`_CHROMIUM_RESOURCE_FLAGS`/`_CHROMIUM_FILE_ACCESS_FLAGS`) — edit those, not call sites, to tune flags. On macOS: install Playwright's `chrome-headless-shell` (`pip install playwright && playwright install chromium-headless-shell`), then put a wrapper script (not a symlink — breaks with SIGTRAP) on `PATH` named `chromium-headless-shell` doing `exec "<real path>" "$@"`.
- Render time for Chrome-based custom plugins (calendar_auth, weather_de, abfahrtzeiten, regenalarm) is usually dominated by the network fetch, not the screenshot — measure both separately before optimizing render.
- **CSS build**: `src/static/styles/main.css` is generated from `partials/*.css` per `_imports.css`'s `@import` list — edit partials, not `main.css`. Rebuild: `python3 scripts/build/build_css.py` (`--minify` for production, `--check` for dry-run). `scripts/dev/dev_watch.sh` auto-rebuilds on save (needs `watchdog`).
- **JS/CSS production bundling**: `scripts/build/build_assets.py` bundles+minifies+content-hashes into `src/static/dist/` (gitignored), wired into `install.sh`/`update.sh` via `install/_common.sh::build_css_bundle()`. Two JS bundles — `common-sync.<hash>.min.js` (non-deferred) and `common-deferred.<hash>.min.js` (deferred) — matching `base.html`'s sync/deferred grouping; don't collapse into one. `base.html`'s `{% if bundled_assets_enabled %}` picks the bundle when `dist/manifest.json` exists and is non-empty. Adding a new global script to `base.html` also needs an entry in `JS_MANIFEST_SYNC`/`JS_MANIFEST_DEFERRED` in `build_assets.py` — only `tests/test_asset_bundling.py` catches drift, and only for files it already knows about. Page-specific scripts (e.g. `ui_helpers.js`, `dark_mode.js`) aren't bundled. `/static/dist/*` gets forced 1-year immutable caching (`security_middleware.py`); everything else under `/static/` stays no-cache. To test the bundled path locally: run `build_assets.py`, restart the dev server (manifest reads once at startup), remove `src/static/dist/` after — `dev_watch.sh` doesn't sync the dist bundle automatically.
- **Response compression**: `apply_response_compression()` (`app_setup/compression.py`) runs last in `security_middleware.py`'s after-request pipeline (it rewrites `Content-Length`, adds `Content-Encoding`/`Vary`). Gzip always on; brotli when the client accepts it and the optional `brotli` package is importable. Only compresses text-ish mimetypes above a size floor — never SSE's `text/event-stream`. `/static/dist/*` responses cache their compressed bytes in-process by path.
- Waitress's thread pool (`_get_web_threads()` in `inkypi.py`) defaults to 2 in production, 8 in dev (`INKYPI_WEB_THREADS` overrides either). At 2 threads, one open dashboard SSE tab (`GET /api/events`, held for the tab's lifetime) plus one slow render (`/preview_now`, `/update_now`) leaves zero free — everything else hangs. SSE's `max_subscribers` cap (50) doesn't protect against this.
- **Pixel-diff snapshot tests are disabled in CI** (`tests/integration/test_visual_regression.py`, `tests/snapshots/` — not run by the `browser-smoke` job) — baselines need Docker+`ubuntu:24.04` to regenerate and had drifted badly; see `tests/snapshots/README.md` for status and how to re-enable.

## Custom plugin notes (abfahrtzeiten, calendar_auth, cal_abfahrt, regenalarm, weather_de)

- **`abfahrtzeiten`**: departure board for German public transit (BVG/VBB/DB HAFAS-wrapper APIs, keyless, CORS-permissive). Prioritizes VBB/BVG inside a Berlin/Brandenburg bounding box, falls back to DB elsewhere. Per-stop fetch failures are isolated — only raises if every stop fails. Settings: `abfahrtzeiten-stops` widget (address→nearby-stops→line/direction wizard). Entries are one JSON blob per stop (`entries[]`, 5 fields) rather than parallel arrays. Result-list rendering uses DOM/`textContent`, not `innerHTML`, for untrusted API text.
- **`calendar_auth`** ("Calendar with Login"): clone of the built-in `calendar` plugin adding per-calendar HTTP Basic Auth. Only a credential label is stored in plugin settings — the password lives in `CALENDAR_AUTH_PASSWORD_<LABEL>` via custom secrets, since the settings-page route re-embeds full instance settings as JSON on every edit (plaintext round-trip). Settings: `calendar-auth-repeater` widget, parallel bracket-arrays (`calendarAuthURLs[]`/`Colors[]`/`Usernames[]`/`Labels[]`).
- **`cal_abfahrt`** ("Calendar + Departures"): combines `calendar_auth`'s agenda with `abfahrtzeiten`'s departures. Reuses both plugins' widgets and exact field names (and the same `CALENDAR_AUTH_PASSWORD_<LABEL>` secrets), but the data-acquisition code is a self-contained copy, not a shared import. Layout picked via `cal-abfahrt-layout`, a pure HTML/CSS widget with no JS initializer — `initializeWidgets()` no-ops when a widget type has no entry in `widgetInitializers`. `board` = merged chronological list (most rows); `grid` = per-stop cards (most legible); each has its own CSS file, inlined at render time by layout.
  - **Renders with zero JavaScript**, unlike `calendar`/`calendar_auth` (which ship FullCalendar into headless Chromium) — plain server-rendered HTML.
  - **Calendar and departure fetches share one `ThreadPoolExecutor`** — total latency is the slowest single request, not the sum. Fetch, parse, and `recurring_ical_events` expansion all happen inside the worker.
  - **ICS bytes decode as UTF-8 explicitly** (`response.content.decode`), never `response.text` — `requests`' charset detection is expensive on a large `.ics`, and RFC 5545 mandates UTF-8 anyway. Apply this to any new ICS-fetching code.
  - Departure requests set `pretty=false&linesOfStops=false&subStops=false&entrances=false` to shrink the response. `remarks` stays on — it's a cancellation signal.
  - **Content budget per layout is decided in Python, in literal pixels** (`constants.py`'s `LAYOUT_METRICS`, `_content_box()`, `_fit_days()`), not left to `overflow:hidden` clipping. These numbers are measured against the CSS — changing a line-height in either stylesheet means re-measuring.
- **`regenalarm`**: German rain radar dashboard for a single location (reverse-engineered `regenonline.de` protocol; `_regenalarm/` at repo root is unused scratch research). Renders via HTML/CSS/Chrome, not Pillow — panel sizing uses literal pixel values (`_layout_px()`) because the in-use `chrome-headless-shell` build mis-paints boxes sized with dynamic CSS units (`dvh`/`%`/flex-grow). Settings reuse `weather-map`. Upstream data refreshes ~every 15 minutes — don't set the playlist interval below that.
- **`weather_de`** ("Weather (Germany)"): clone of `weather` adding **Bright Sky** (`api.brightsky.dev`, free/keyless DWD wrapper) as a third provider — sunrise/sunset come from `astral`, UV/AQI reuse Open-Meteo's air-quality endpoint, feels-like falls back to actual temperature. `openMeteoModel` setting pins Open-Meteo to DWD's ICON-D2 model (no `precipitation_probability`, parsing is null-safe). Has 8-language localization, not present in the built-in `weather` plugin. OpenWeatherMap key is required only when that provider is selected.
